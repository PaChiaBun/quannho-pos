## 1. Executive Summary & Installation Strategy

### 1.1 Strategy Statement: Deterministic Fail-Fast Forward Migration Suite
Production Database PostgreSQL catalog analysis (`CONFIRMED_PG_CATALOG`, 13/08/2026) confirmed that **zero (0) QR V3 or Legacy QR objects exist** in the `public` schema. Therefore, Architecture v3 is designed as a **DETERMINISTIC FAIL-FAST FORWARD MIGRATION SUITE** on top of the existing Production schema.

- **Clean Installation Base:** The migration suite installs cleanly on top of existing core tables.
- **Fail-Fast Preflight Validation:** If any target QR object unexpectedly exists on the database during migration execution, preflight checks MUST inspect its exact type, signature, and constraints. If the existing object does not match the contract, the preflight script MUST issue `RAISE EXCEPTION` to halt execution immediately.
- **No Concealed Drift:** `IF NOT EXISTS` constructs will NOT be used to bypass or conceal schema drift.
- **Legacy Files Touch Rule:** Legacy QR migration files (`migration_qr_ordering.sql`, `migration_kay_public_ordering_v2.sql`, `20260731_*_v3.sql`) will NOT be executed, modified, or referenced as a deploy chain.
- **No CASCADE Drops:** `CASCADE` drop operations are STRICTLY FORBIDDEN.
- **Preflight & Postflight Requirement:** Every migration file must contain an explicit preflight validation block at the top and a postflight integrity check block at the bottom.
- **Staging Blocked Enforcement:** Because Staging (`quannho-staging.lpm.vn`) remains `BLOCKED_STAGING`, Phase 2 will write canonical SQL files ONLY and will NOT execute them until Staging DB or Supabase Studio SQL Editor access is active.

## 3. Channel Code, Tracking Token & Idempotency Resolution

### 3.1 Channel Code Specification
- **Entropy & Format:** Minimum 128-bit random entropy (32 hexadecimal characters prefixed with `tbl_` or `ctr_`, e.g. `tbl_a1b2c3d4e5f67890a1b2c3d4e5f67890`).
- **Database Unique Guard:** `ALTER TABLE public.qr_channels ADD CONSTRAINT uq_qr_channels_code UNIQUE (channel_code);`
- **Format & Type Matching Constraint:**
  ```sql
  CONSTRAINT chk_qr_channels_code_format CHECK (
    (type = 'table' AND channel_code ~ '^tbl_[0-9a-f]{32}$')
    OR
    (type = 'counter' AND channel_code ~ '^ctr_[0-9a-f]{32}$')
  )
  ```
- **Predictability:** Channel code contains NO guessable store ID or table ID elements.
- **Allocation Retry:** If channel generation hits a unique collision, the allocation function retries up to 5 times before failing.
- **Audit Masking:** Full channel code is NOT logged in application audit logs.

### 3.2 Customer Tracking Token Resolution Protocol
To resolve client response loss during order submission:
1. **Client Token Generation:** The Flutter client generates a raw 256-bit tracking token (`p_tracking_token`, 64 lowercase hex characters) using a cryptographically secure random generator **BEFORE** making the initial RPC submit call.
2. **State Persistence Across Retries:** The client controller state retains both `p_idempotency_key` and `p_tracking_token` for all retry attempts of the same order submit.
3. **RPC Signature:**
   ```sql
   submit_qr_order_v3(
     p_channel_code     text,
     p_items            jsonb,
     p_note             text,
     p_idempotency_key  text,
     p_tracking_token   text
   ) RETURNS jsonb
   ```
4. **Token Format Validation:** Server validates `p_tracking_token ~ '^[0-9a-f]{64}$'`. If invalid, returns error `INVALID_TRACKING_TOKEN_FORMAT`.
5. **Database Hashing:** The database stores ONLY `tracking_token_hash := digest(convert_to(p_tracking_token, 'UTF8'), 'sha256')`. Raw tracking tokens are NEVER stored or logged.
6. **Retry Validation Protocol:**
   - On retry matching `channel_id` and `idempotency_key`:
     - If `request_payload_hash` matches AND `tracking_token_hash` matches: Return existing `request_id`, `pickup_code`, `status`, `created_at` with `is_duplicate: true`.
     - If `idempotency_key` matches BUT `tracking_token_hash` differs: Return error `IDEMPOTENCY_TOKEN_MISMATCH`.
     - If `idempotency_key` matches BUT `request_payload_hash` differs: Return error `IDEMPOTENCY_MISMATCH`.
7. **Status Lookup (`get_qr_request_status_v3`):** Hashes `p_tracking_token` input (`digest(convert_to(p_tracking_token, 'UTF8'), 'sha256')`) and queries matching `tracking_token_hash`.

### 3.3 Canonical Payload Hash Algorithm
Payload canonicalization before computing `request_payload_hash`:
1. Validate `p_items` is a JSON array.
2. Validate each item object contains strictly: `product_id` (lowercase UUID), `quantity` (integer > 0), `modifiers` (array of lowercase topping UUIDs). Unexpected fields cause rejection with error `INVALID_PAYLOAD_FORMAT`.
3. Normalize product UUIDs and topping UUIDs to lowercase strings.
4. Sort topping UUIDs within each item alphabetically.
5. **Item Duplicate Rule:** Reject submit payloads containing duplicate `product_id` + identical `modifiers` with error `DUPLICATE_PAYLOAD_ITEM` (requiring client to combine quantities before submit).
6. Sort item list alphabetically by `product_id` then concatenated `modifiers`.
7. Trim `p_note` (`TRIM(COALESCE(p_note, ''))`).
8. Compute payload hash: `v_payload_hash := digest(convert_to(v_canonical_json::text, 'UTF8'), 'sha256')`.
9. The identical canonical representation is used for both initial insert and retry comparisons.

## 4. Legacy Table-ID Compatibility & Fail-Closed Policy

### 4.1 Structural Reality (`CONFIRMED_PG_CATALOG`)
Production schema catalog confirms:
- `ban_dining_tables.id`: Defined as `text`. Contains 103 UUID-like string IDs and 2 active non-UUID string IDs.
- `ban_sessions.table_id`: Defined as `uuid` (has no FK to `ban_dining_tables`).

### 4.2 Fail-Closed Compatibility Rules
1. **Text Reference Storage:** `qr_channels.table_id` and `qr_requests.table_id` are defined as `text`.
2. **Dispatch Type Guard (`send_to_kitchen_qr_v3`):**
   - When dispatching a table order to `ban_sessions`, `send_to_kitchen_qr_v3` attempts to parse `table_id` as UUID.
   - If `table_id` fails UUID parsing, dispatch IMMEDIATELY fails with error `TABLE_ID_NOT_QR_COMPATIBLE`.
3. **No Migration ID Alteration:** QR migrations will NOT alter primary keys of existing `ban_dining_tables` rows.
4. **Non-UUID Table Restriction:** The 2 active non-UUID tables are marked `TABLE_ID_NOT_QR_COMPATIBLE`. Phase 3 Flutter UI MUST disable QR code generation/printing for these 2 tables and display an admin notice.
5. **Data Repair Boundary:** Data repair of the 2 legacy non-UUID tables is a separate core task requiring separate approval.
6. **No Deterministic Fake UUIDs:** Generating deterministic fake UUIDs is STRICTLY FORBIDDEN because `ban_screen` and `pos_screen` will fail to query active sessions.

## 6. Authorization & Permission Contract

### 6.1 Canonical Action Keys (Exact 8 Keys Only)
The 8 canonical action keys are:
1. `qr_order.view_pending`: Access incoming QR order queue.
2. `qr_order.claim`: Claim an incoming `pending_staff` request.
3. `qr_order.reject`: Reject a request from `pending_staff`, `processing`, or `confirmed`.
4. `qr_order.confirm`: Verify request details and confirm order.
5. `qr_order.send_kitchen`: Dispatch `confirmed` order to kitchen and core tables.
6. `qr_order.manage_channels`: Generate, activate, rotate, or disable table/counter QR codes.
7. `qr_order.print_qr`: Access QR design preview and trigger client PDF export.
8. `qr_order.manage_settings`: Configure QR settings, pairing codes, device session bootstrap, and admin session revocation.

*(Note: Self-revoking one's own active session via `revoke_pos_device_session_v3` requires ONLY a valid session token and does NOT require `qr_order.manage_settings`. `qr_order.pair_device` is REMOVED).*

### 6.2 Permission Resolution Algorithm (`check_pos_staff_action_permission`)
1. **Context & Principal Extraction:**
   ```sql
   check_pos_staff_action_permission(
     p_store_id        uuid,
     p_staff_id        uuid,
     p_user_account_id uuid,
     p_action_key      text
   ) RETURNS boolean
   ```
2. **Membership & Status Verification:**
   - If `p_staff_id` is present, verify `staff_members.id = p_staff_id AND store_id = p_store_id AND is_active = true`.
   - If `p_user_account_id` is present, verify `store_members.user_id = p_user_account_id AND store_id = p_store_id`.
   - If membership check fails, return `false` (Fail-Closed).
3. **Owner Privilege Override:** If `store_members.is_owner = true`, return `true`.
4. **Manager Privilege Alignment:** If staff role is `owner` or `manager`, grant full 8 QR action keys after store membership is verified, matching current Flutter implementation (`StaffService.getActionPermissions`). Manager is NOT restricted by `app_settings` in V3.
5. **Other Roles Action Lookup:**
   - Fetch `app_settings` where `store_id = p_store_id AND key = 'action_perms_' || v_role_string`.
   - Try exact role string match first (e.g. `action_perms_Thu ngân`, `action_perms_Phục Vụ`).
   - If missing, try canonical role key fallback (`Thu ngân` $\rightarrow$ `cashier`, `Phục Vụ` $\rightarrow$ `waiter`, `Bếp` $\rightarrow$ `kitchen`, `Quản Lý` $\rightarrow$ `manager`).
   - If missing or setting does not exist, return `false` (Fail-Closed). Non-manager roles do NOT get default QR permissions.
6. **No Direct Staff Actions Query:** Do NOT query `staff_members.actions` or `store_members.actions`.
7. **Malformed JSON Handling:** Parse JSON text safely. Malformed JSON causes fail-closed `false` and writes a rate-limited audit log entry.

## 7. Counter Pickup Code Allocation Contract

### 7.1 Schema Specification & Constraints (`public.qr_requests`)
```sql
ALTER TABLE public.qr_requests
  ADD COLUMN pickup_business_date date,
  ADD COLUMN pickup_number        integer,
  ADD COLUMN pickup_code          text;

ALTER TABLE public.qr_requests
  ADD CONSTRAINT uq_qr_requests_pickup_sequence
  UNIQUE (store_id, pickup_business_date, pickup_number);

ALTER TABLE public.qr_requests
  ADD CONSTRAINT chk_qr_requests_pickup_mode CHECK (
    (type = 'counter' AND pickup_business_date IS NOT NULL AND pickup_number IS NOT NULL AND pickup_code IS NOT NULL)
    OR
    (type = 'table' AND pickup_business_date IS NULL AND pickup_number IS NULL AND pickup_code IS NULL)
  );

ALTER TABLE public.qr_requests
  ADD CONSTRAINT chk_qr_requests_pickup_number_positive CHECK (
    pickup_number IS NULL OR pickup_number > 0
  );

ALTER TABLE public.qr_requests
  ADD CONSTRAINT chk_qr_requests_pickup_code_format CHECK (
    pickup_code IS NULL OR pickup_code ~ '^Q[0-9]{3,}$'
  );
```

### 7.2 Idempotency & Pickup Allocation Sequence
1. **Idempotency Preflight:** Idempotency key lookup MUST be performed BEFORE allocating a new pickup number. If a matching idempotency key is found for the channel, return the existing request and existing `pickup_code` immediately.
2. **Business Date Determination:** Calculate `v_date := (now() AT TIME ZONE 'Asia/Ho_Chi_Minh')::date`.
3. **Transaction-Level Advisory Lock:**
   ```sql
   PERFORM pg_advisory_xact_lock(
     hashtext(v_store_id::text || '_counter_seq_' || v_date::text)
   );
   ```
4. **Sequence Allocation:**
   ```sql
   SELECT COALESCE(MAX(pickup_number), 0) + 1 INTO v_seq
   FROM public.qr_requests
   WHERE store_id = v_store_id
     AND pickup_business_date = v_date
     AND type = 'counter';
   ```
5. **Format Display Code:** `v_pickup_code := 'Q' || LPAD(v_seq::text, 3, '0');` (e.g. `Q001`, `Q002`).
6. **No `#Q01` Fallback / No Unlocked `COUNT(*)`:** Hardcoded `#Q01` fallbacks or unlocked `COUNT(*)` queries are STRICTLY FORBIDDEN.

## 9. Authentication, Hashing & Deterministic Rate-Limiting Realities

### 9.1 Credential Hashing Specification (Production Alignment)
Production codebase inspection (`lib/core/services/user_auth_service.dart:L46`) confirms the canonical password/PIN hash formula:
```text
SHA256(phone + ':' + credential + ':qn_pos_2024_salt')
```
In SQL, Phase 2 creates internal helper `public.hash_pos_credential_v3(p_phone text, p_credential text) RETURNS text`:
```sql
CREATE OR REPLACE FUNCTION public.hash_pos_credential_v3(
  p_phone      text,
  p_credential text
) RETURNS text
LANGUAGE sql
IMMUTABLE STRICT
SET search_path = public, pg_temp
AS $$
  SELECT encode(
    digest(convert_to(p_phone || ':' || p_credential || ':qn_pos_2024_salt', 'UTF8'), 'sha256'),
    'hex'
  );
$$;
```
*(Note: Function is STRICT; inputs must not be null).*

Canonical V3 Credential Verification Rules:
- `owner_password`: Phone-salted hash via `hash_pos_credential_v3(user_accounts.phone, p_credential)`.
- `manager_quick_pin`: Phone-salted hash via `hash_pos_credential_v3(user_accounts.phone, p_credential)`.
- `staff_pin`: Raw PIN SHA-256 text hex via `encode(digest(convert_to(p_credential, 'UTF8'), 'sha256'), 'hex')`.

Preflight in Phase 2 verifies `staff_members.pin_hash` format (verifying NULL or 64-character lowercase hex string `^[0-9a-f]{64}$`). No runtime algorithm branching.

### 9.2 Authentication RPC Signature & Verification Rules
```sql
issue_pos_device_session_v3(
  p_store_code   text,
  p_auth_mode    text,
  p_principal_id uuid,
  p_credential   text,
  p_device_id    uuid
) RETURNS jsonb
```

Verification Protocol:
1. **Store Bootstrap Verification (`pos_store_bootstrap_state`):** Bootstrap status is checked explicitly against table `pos_store_bootstrap_state` (`WHERE store_id = v_store_id`).
2. **`staff_pin` Mode:** `p_principal_id` MUST be a valid `staff_members.id` belonging to `p_store_code` where `is_active = true`. Compares `staff_members.pin_hash` directly against raw PIN SHA-256 text hex. Does NOT scan all staff members.
3. **`manager_quick_pin` Mode:** `p_principal_id` MUST be a valid `user_accounts.id`. Verifies `store_members` membership for `p_store_code` (`is_owner = true` or manager role). Compares phone-salted quick PIN text hex.
4. **`owner_password` Mode:** `p_principal_id` MUST be a valid `user_accounts.id` with `store_members.is_owner = true`. Compares phone-salted password text hex.
5. **Session Revocation on Issue:** If an active session exists for `(store_id, device_id)` where `revoked_at IS NULL`, `issue_pos_device_session_v3` revokes the old session (`revoked_at := now()`) before inserting the new session within the SAME atomic transaction, enforcing `idx_pos_single_active_session`.

### 9.3 Safe Pairing Protocol
- `pair_pos_device_v3`: Consumes pairing code, creates `devices` entry, returns `device_id` and `device_role`.
- **DOES NOT create `pos_device_sessions` and DOES NOT return `session_token`**.
- After pairing, staff MUST call `issue_pos_device_session_v3` with principal ID + PIN/password to log in and receive a session token.

### 9.4 Deterministic Rate-Limiting Algorithm (No Credentials in Bucket)
Table `pos_auth_attempts` enforces deterministic rate limiting:
- **Identifier Hash Determination (No Credentials Included):**
  - For `staff_pin`, `manager_quick_pin`, `owner_password`:
    `v_identifier_hash := digest(convert_to(p_principal_id::text, 'UTF8'), 'sha256');`
  - For `pairing_code`, `bootstrap` (before principal exists):
    `v_identifier_hash := digest(convert_to(v_store_id::text || ':' || p_attempt_type, 'UTF8'), 'sha256');`
- **Normalized First Forwarded IP Extraction:**
  `v_ip := TRIM(SPLIT_PART(COALESCE(current_setting('request.headers', true)::json ->> 'x-forwarded-for', '0.0.0.0'), ',', 1));`
- **Lockout Remaining Calculation:**
  ```sql
  SELECT GREATEST(0, EXTRACT(EPOCH FROM (MIN(created_at) + INTERVAL '15 minutes' - now())))::integer INTO v_remaining_seconds
  FROM public.pos_auth_attempts
  WHERE store_id = v_store_id
    AND attempt_type = p_attempt_type
    AND identifier_hash = v_identifier_hash
    AND ip_address = v_ip
    AND is_success = false
    AND created_at > (now() - INTERVAL '15 minutes')
    AND created_at > COALESCE((
      SELECT MAX(created_at)
      FROM public.pos_auth_attempts
      WHERE store_id = v_store_id
        AND attempt_type = p_attempt_type
        AND identifier_hash = v_identifier_hash
        AND ip_address = v_ip
        AND is_success = true
    ), '1970-01-01'::timestamptz);
  ```
- **Deterministic Reset:** Inserting `is_success = true` on valid authentication resets the active failed count for subsequent rate limit calculations. 5 different wrong credential guesses for the same principal/IP trigger `RATE_LIMITED` on the 6th attempt. Raw PINs, passwords, and pairing codes are NEVER logged in `pos_auth_attempts`.

## 10. Standardized State Machine, Expiry Policy & Re-Confirmation

### 10.1 State Machine Graph & Transition Rules
```text
                  ┌───────────────────────────────────────────────┐
                  │                                               │
                  ▼                                               │
[Customer Submit] ──► pending_staff ──► processing ──► confirmed ─┴─► sent_kitchen
                           │                               │
                           ├───────────────────────────────┴────────► rejected
                           │
                           └────────────────────────────────────────► expired
```

| Current State | Target State | Action Key Required | Allowed Actor | Transition Rules & Actions |
|---|---|---|---|---|
| `(None)` | `pending_staff` | *(Public)* | Customer | Active channel, menu active, settings enabled. |
| `pending_staff` | `processing` | `qr_order.claim` | POS Staff | Row lock `FOR UPDATE`. Sets `claimed_by_*`. |
| `processing` | `confirmed` | `qr_order.confirm` | POS Staff | Revalidates server prices, updates item snapshots, increments `quote_version`. |
| `pending_staff` | `rejected` | `qr_order.reject` | POS Staff | Reason required. Row lock `FOR UPDATE`. |
| `processing` | `rejected` | `qr_order.reject` | POS Staff | Reason required. Row lock `FOR UPDATE`. |
| `confirmed` | `rejected` | `qr_order.reject` | POS Staff | Reason required. Row lock `FOR UPDATE`. Prevents stuck orders. |
| `confirmed` | `sent_kitchen` | `qr_order.send_kitchen` | POS Staff | Revalidates against `quote_version`. Atomic dispatch to core tables. |
| `confirmed` | `processing` | *(System Auto)* | System | Triggered by `send_to_kitchen_qr_v3` when price/availability discrepancy detected. |
| `pending_staff` | `expired` | *(Maintenance)* | System Cron | Expire after 30 minutes unhandled (`created_at < now() - INTERVAL '30 minutes'`). |

### 10.2 V1 Expiry Rules
- Unclaimed `pending_staff` requests expire after 30 minutes.
- `processing` and `confirmed` requests do NOT auto-expire in V1 (staff has taken ownership).
- Maintenance RPC `cleanup_expired_qr_requests_v3()` acquires `FOR UPDATE SKIP LOCKED` lock, updates status to `expired`, writes audit log `expire_request`, and NEVER alters `sent_kitchen` or `rejected` requests. Executable ONLY by `service_role`.

### 10.3 Confirmation & Re-Confirmation Protocol
1. **Confirmation (`confirm_qr_request_v3`):**
   - Re-query all products and toppings from `public.products` under `FOR SHARE` lock.
   - Update `qr_request_items` (`product_name`, `unit_price`, `subtotal`, `modifiers_json` topping snapshots) with current server prices.
   - Update `qr_requests.total_amount`.
   - Increment `quote_version := quote_version + 1`.
   - Update `status = 'confirmed'`.
   - Return confirmed quote JSON payload to Flutter.
2. **Re-Confirmation Protocol (`send_to_kitchen_qr_v3`):**
   - Re-query live product prices, availability (`is_available = true`, `is_active = true`, `is_deleted = false`), and valid topping links.
   - Compare item-by-item prices, quantities, and topping snapshots against `qr_request_items`.
   - **Discrepancy Trigger:** If any price differs, or if any product/topping is unavailable/deleted/unlinked:
     - **DO NOT** create any core records (`orders`, `ban_session_items`, `kitchen_tickets`).
     - Transition request status `confirmed -> processing`.
     - Return `ORDER_RECONFIRM_REQUIRED` along with detailed item discrepancy list.
     - Write audit log entry `price_discrepancy_revert`.
     - Staff UI displays discrepancy details to staff. Staff reviews with customer and calls `confirm_qr_request_v3` again to update snapshots and increment `quote_version`.

## 12. Core Dispatch Mapping & Mixed Station Architecture

### 12.1 Core Order Status Alignment (`CONFIRMED_PG_CATALOG`)
Production catalog audit and POS codebase confirm existing core `orders.status` value for newly created POS orders is `'open'`.
- Core Order Creation: `orders.status := 'open'`.
- Source Type: `orders.source_type := 'qr_order'`.
- Source ID: `orders.source_id := v_req.id::text`.
- Unique Partial Order Guard:
  ```sql
  CREATE UNIQUE INDEX idx_orders_one_per_qr_request
  ON public.orders (store_id, source_id)
  WHERE source_type = 'qr_order';
  ```

### 12.2 Branch A: TABLE Dispatch Contract
- `table_id` (`text`) MUST parse to a valid UUID. If non-UUID, return error `TABLE_ID_NOT_QR_COMPATIBLE`.
- Acquire table advisory lock: `PERFORM pg_advisory_xact_lock(hashtext(v_store_id::text || '_table_session_' || v_table_uuid::text));`
- Reuse existing open session (`ban_sessions` where `status = 'open'`) or insert a new `ban_sessions` record.
- Open Session Unique Partial Guard:
  ```sql
  CREATE UNIQUE INDEX idx_ban_sessions_one_open_per_table
  ON public.ban_sessions (store_id, table_id)
  WHERE status = 'open' AND table_id IS NOT NULL;
  ```
- Insert `ban_session_items` (`modifiers_json::text`).
- Insert `orders` (`status = 'open'`, `source_type = 'qr_order'`, `source_id = v_req.id::text`) and `order_items`.
- Lock parent session row (`SELECT id FROM public.ban_sessions WHERE id = v_session_id FOR UPDATE;`).
- Calculate `round := COALESCE(MAX(round), 0) + 1`.
- Unique Round Guard:
  ```sql
  ALTER TABLE public.kitchen_tickets
    ADD CONSTRAINT uq_kitchen_tickets_session_round UNIQUE (session_id, round);
  ```

### 12.3 Branch B: COUNTER Dispatch Contract
- **DO NOT** create fake `ban_dining_tables` or `ban_zones`.
- **DO NOT** create or open a `ban_sessions` record.
- Insert POS `orders` (`status = 'open'`, `source_type = 'qr_order'`, `source_id = v_req.id::text`) and `order_items`.
- Create single `kitchen_tickets` record: `session_id = NULL`, `round = 1`, `table_label = 'Mang đi ' || pickup_code`, `zone_label = 'Mang đi'`, `station_code = NULL` (if mixed stations).
- Insert `kitchen_ticket_items` with `session_item_id = NULL` and individual normalized `station_code`.
- POS uses `order_id` / `source_id` for checkout.

### 12.4 Mixed Station Ticket Contract
- Exactly **ONE** `kitchen_tickets` record is created per request/round to comply with `UNIQUE (session_id, round)`.
- If a request contains items for multiple stations (e.g. both `nong` and `bar`), `kitchen_tickets.station_code` is set to `NULL`.
- Each `kitchen_ticket_items` record MUST have its own individual normalized `station_code` (`nong` or `bar`).
- Kitchen displays and station printers filter and route items based on `kitchen_ticket_items.station_code`.

### 12.5 Duplicate Dispatch Retry Behavior
If `send_to_kitchen_qr_v3` is invoked on a request already in `sent_kitchen`, the RPC re-queries existing `orders.id` via `idx_orders_one_per_qr_request` and returns `is_duplicate_dispatch: true` without creating duplicate core records.

## 13. Settings JSON Schema & Channel Lifecycle

### 13.1 `qr_order_settings` Exact JSON Schema
Stored in `public.app_settings` (`key = 'qr_order_settings'`):
```json
{
  "is_table_enabled": false,
  "is_counter_enabled": false,
  "auto_claim": false,
  "sound_enabled": true,
  "public_domain": ""
}
```
- **Key Validation:** Unknown keys cause rejection with error `QR_SETTINGS_INVALID`.
- **Type Validation:** `is_table_enabled` (bool), `is_counter_enabled` (bool), `auto_claim` (bool), `sound_enabled` (bool), `public_domain` (string). Null or incorrect types cause rejection with error `QR_SETTINGS_INVALID`.
- **Domain Validation:** `public_domain` must be trimmed, max length 255, and must match HTTPS origin format `^https://[a-zA-Z0-9.-]+(:[0-9]+)?$` or empty string `""`. Must NOT contain path, query, or hash fragments.
- **Merge Behavior:** Missing row returns complete defaults. Existing row missing keys merges with defaults.

### 13.2 Channel Lifecycle & Rotation Contract
- **TABLE Channels:** Maximum 1 active channel per `table_id` per store (`CREATE UNIQUE INDEX idx_qr_channels_active_table ON public.qr_channels(store_id, table_id) WHERE type = 'table' AND is_active = true;`).
- **COUNTER Channels:** Maximum 1 active counter channel per store (`CREATE UNIQUE INDEX idx_qr_channels_active_counter ON public.qr_channels(store_id) WHERE type = 'counter' AND is_active = true;`).
- **Upsert Behavior (`upsert_qr_channel_v3`):** If an active channel already exists for the table/counter, returns existing active channel without rotating.
- **Rotation Endpoint (`rotate_qr_channel_v3`):** Requires `qr_order.manage_channels`. Deactivates current channel (`is_active = false`) and creates a new channel code in a single transaction. Writes audit event `rotate_channel` (channel code masked).
- **Activation Status Endpoint (`set_qr_channel_active_v3`):** Writes audit event `activate_channel` when `p_is_active = true`, or `disable_channel` when `p_is_active = false`. Attempting to activate a channel when an active channel already exists returns `CHANNEL_ACTIVE_CONFLICT`.

## 14. Transaction Boundary & Exception Wording

### 14.1 Business State Transitions (Commit Permitted)
The following business validation outcomes represent **intentional business state transitions** and ARE PERMITTED TO COMMIT:
- **`ORDER_RECONFIRM_REQUIRED`:** Price/availability discrepancy detected during dispatch. Updates request status `confirmed -> processing`, writes `price_discrepancy_revert` audit event, and returns JSON payload with discrepancy preview data (`success: false`).
- **`UNKNOWN_STATION_CODE`:** Product station code invalid/missing. Reverts request status to `processing`, writes `unknown_station_revert` audit event, and returns JSON payload (`success: false`).

### 14.2 Technical Failure Boundary (Atomic Rollback)
- **Pre-Mutation Validation Gate:** ALL price, availability, topping link, table compatibility, station, and permission checks MUST complete 100% BEFORE starting core table inserts (`orders`, `order_items`, `ban_sessions`, `ban_session_items`, `kitchen_tickets`, `kitchen_ticket_items`).
- **Technical Failures:** Any unhandled database exception or constraint failure occurring after core insertion begins MUST execute `RAISE EXCEPTION` to enforce a 100% PostgreSQL transaction rollback. Core inserts will NEVER be committed partially.

## 15. RLS Policies & Security Isolation

### 15.1 Out-Of-Scope Core Security Debt (`OUT_OF_SCOPE_EXISTING_CORE_SECURITY_DEBT`)
Existing core tables (`products`, `ban_sessions`, `orders`, `app_settings`) allow direct CRUD to `anon` via permissive RLS policies (`ALL USING (true)`). **QR V3 migrations MUST NOT alter existing core table grants or RLS policies** to prevent breaking existing POS operations.

### 15.2 Comprehensive RLS Enforcement for ALL 9 New Tables
All 9 new QR tables MUST explicitly execute `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`, and `REVOKE ALL ON TABLE public.<table_name> FROM PUBLIC, anon, authenticated;`:
1. `public.qr_channels`
2. `public.qr_requests`
3. `public.qr_request_items`
4. `public.qr_audit_logs`
5. `public.product_topping_links`
6. `public.pos_device_sessions`
7. `public.pos_store_bootstrap_state`
8. `public.store_pairing_codes`
9. `public.pos_auth_attempts`

Function Ownership & Grants:
- All RPCs defined with `SECURITY DEFINER`, owned by `postgres` role (`ALTER FUNCTION public.<func_name> OWNER TO postgres;`), with fixed `SET search_path = public, pg_temp;`.
