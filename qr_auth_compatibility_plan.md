# Architecture v3: Hybrid Edge/RPC POS QR Authorization & State Machine Plan
File: `qr_auth_compatibility_plan.md`

This document defines **Architecture v3** for **Quán Nhỏ POS & Website KAY QR Order Authorization**. It aligns the QR security design with the actual Quán Nhỏ Custom Auth architecture, eliminating reliance on Supabase Native Auth (`auth.uid()`) while enforcing strict zero-trust cryptographic token verification and atomic state transitions.

> [!IMPORTANT]

> 1. **No Supabase Auth JWT:** Quán Nhỏ POS operates exclusively on Custom Auth (`user_accounts`, `store_members`, `staff_members`, `SharedPreferences`). `auth.uid()` is NULL for POS requests using the anon key. RPCs MUST NOT use `auth.uid()`.
> 2. **Client Headers Are Untrusted:** Headers `x-store-id` and `x-user-id` are passed by the client for routing/isolation ONLY. They MUST NEVER be trusted for authentication or privilege authorization.
> 3. **QR Security Scope Isolation:** QR Security Migration is strictly isolated to the QR Order module. It MUST NOT revoke table access or alter baseline schemas of core auth tables (`user_accounts`, `store_members`, `staff_members`).
> 4. **Multi-Source Permission Lookup:** Membership & roles reside in `store_members`. Operational active status resides in `staff_members`. Action permissions follow: `store_members.actions` $\rightarrow$ `staff_members.actions` $\rightarrow$ `app_settings` $\rightarrow$ default perms.

## 🏛️ 2. HYBRID AUTHENTICATION MODEL & TOKEN LIFECYCLE

### 2.1 Customer Facing (Anonymous Public API)
- Customers access public RPCs ONLY:
  - `get_qr_menu(p_channel_code)`
  - `submit_qr_order(p_channel_code, p_items, p_note, p_idempotency_key)`
  - `get_qr_request_status(p_tracking_token)`
- **Server-Side Validation:** All prices, store isolation, channel validity, stock availability, and topping links are computed dynamically on the server. Client-submitted prices are ignored.
- **No Direct Table Access:** Anonymous users are strictly denied direct `SELECT`, `INSERT`, `UPDATE`, `DELETE` on all `qr_*` tables.

### 2.2 POS Staff Facing (Cryptographic Session Tokens & Bootstrap Modes)
- **Token Issuance Bootstrap Modes (`issue_pos_device_session`):**
  - **Mode A: Owner/Manager Pairing Code:** Short-lived 6-digit pairing code generated by owner/manager, hashed via HMAC-SHA-256 in Deno runtime or DDL helper.
  - **Mode B: Staff Credential Verification:** Validates store PIN/Password against hashed store PINs in `staff_members`.
  - **Strict Security Rules:** Both modes MUST be rate-limited, logged/audited, and MUST NOT accept `user_id` or `store_id` supplied by the client as authority source!
- **Token Storage & Lifecycle Rules:**
  - Raw 256-bit token is returned **EXACTLY ONCE** to client memory upon issuance.
  - Database stores **ONLY the SHA-256 hash (`token_hash bytea`)**.
  - Client stores token securely using **`flutter_secure_storage`** (iOS Keychain / Android Keystore).
  - **NEVER** store in `SharedPreferences`.
  - **NEVER** write raw token to application logs or server logs.
  - Must rotate or revoke session token upon logout, staff switch, or device change.

## 🔄 3. STANDARDIZED STATE MACHINE & ATOMIC KITCHEN DISPATCH

### 3.1 Strict Status Values
The QR Order state machine uses ONLY the following 6 standardized status values:
- `pending_staff`: Customer submitted order; awaiting POS staff claim.
- `processing`: POS staff claimed order; reviewing order details with customer.
- `confirmed`: Order verified with customer; ready for kitchen dispatch.
- `sent_kitchen`: Order approved and dispatched to kitchen/bar.
- `rejected`: Order rejected by POS staff.
- `expired`: Order timed out without staff claim.

```
[ Customer Submits ] ──► pending_staff
                               │
                               ├─► (Staff Claims) ──► processing
                               │                          │
                               │                          ├─► (Staff Confirms) ──► confirmed
                               │                          │                            │
                               │                          │                            └─► (Send to Kitchen) ──► sent_kitchen
                               │                          │
                               └─► (Staff Rejects) ──────┴─► rejected
```

> [!CAUTION]
> **Strict Transition Rule:** Sending directly to kitchen from `pending_staff` is **STRICTLY FORBIDDEN**. Direct client table update fallbacks in Flutter (`_sb.from('qr_requests').update(...)`) must be **REMOVED 100%**.

### 3.2 Atomic Kitchen Dispatch Transaction (`send_to_kitchen_qr`)
When transitioning `confirmed` $\rightarrow$ `sent_kitchen`, the server-side RPC executes an **atomic single transaction**:
1. Validates staff token, store isolation, and `qr_order.send_kitchen` action permission.
2. Acquires row lock (`FOR UPDATE`) on `qr_requests`.
3. Creates or updates `orders` and `order_items` taking an exact price/name/topping snapshot.
4. Populates `ban_session_items` if table order.
5. Generates `kitchen_tickets` and `kitchen_ticket_items` split by kitchen station (Bep Nong / Bep Bar).
6. Atomically updates `qr_requests.status = 'sent_kitchen'`.
7. `waiter_id` / `staff_id` explicitly references `staff_members.id`.
8. Any failure mid-transaction triggers a 100% rollback.

## 📡 4. REALTIME RESOLUTION FOR MVP (CONTROLLED POLLING)

Because POS operates via Custom Auth with the `anon` key without a valid Supabase Auth JWT, RLS Realtime cannot verify authorization using a POS token RPC. Direct `anon` `SELECT` on `qr_requests` is a **SECURITY VULNERABILITY**.

### MVP Controlled Polling Resolution:
- POS fetches pending requests via RPC `get_pending_qr_requests(p_raw_token, ...)`
- Controlled polling every 3–5 seconds.
- RPC returns ONLY requests matching the token's authenticated `store_id`.
- Polling stops immediately upon logout or when the app goes to background.
- Implements exponential backoff on network errors.
- Pending count stored per store/session (no global `_lastPendingCount`).
- Upgrade to Realtime WebSocket ONLY when secure server broadcast or valid Supabase Auth JWT is established.
